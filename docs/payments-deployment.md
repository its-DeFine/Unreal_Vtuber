# Payments + Orchestrator Deployment Guide

This document reflects the current production layout where the payments backend runs on its own EC2 instance while each Unreal orchestrator lives on a GPU-backed host. It covers the required ports, environment variables, and the registration flow between the two.

---

## 1. Topology Overview

```
+----------------------+              +----------------------+
| Payments EC2         |<---health----|  Unreal Orchestrator |
| (t3.small or similar)|              |  (g4dn.xlarge)       |
|                      |----payouts-->|                      |
| payments backend repo      |        | docker-compose.unreal|
+----------------------+              +----------------------+
                 ^                                  ^
                 |                                  |
         management IPs                     browser clients,
         (SSH/API access)                   Livepeer traffic
```

- **Payments EC2**: runs `payments-backend` and the Fluent Bit collector from the standalone payments backend repository. In production we deploy this compose stack on a **separate EC2 instance** (no GPU required) so the payment loop is isolated from the Unreal workloads.
- **Orchestrator EC2**: runs TURN, signaling, packaged Unreal, script runner, and the registration helper (from `docker-compose.unreal.yml`).
- Multiple orchestrators can report to the same payments backend—the backend monitors each via the `health_url` they register.

## 2. Network Ports

### Orchestrator host inbound

| Port/Proto | Purpose | Exposure |
|------------|---------|---------|
| TCP 22 | SSH (optional) | lock to management IPs |
| TCP 8080 | Pixel Streaming UI | local orchestrator access (use SSH tunnel if viewing remotely) |
| TCP 8888-8889 | WebRTC signaling (HTTP/WS) | local orchestrator access |
| TCP 9001 | Recorder manager control plane | local orchestrator access |
| TCP 9090 | Health endpoint consumed by payments backend | payments EC2 IP only |
| TCP 9876/9877 | Worker/script APIs (voice/FX control) | local orchestrator access (allow backend services as needed) |
| TCP 9995 | Livepeer orchestrator (if enabled) | Livepeer control plane only |
| UDP 3478 | coturn STUN/TURN | optional (only when exposing to external viewers) |
| UDP 19302-19303 | Google STUN fallback | optional; limit to client IP if enabled |
| UDP 40000-49999 & 49160-49200 | TURN media relay ranges (optional – only required when exposing Pixel Streaming to external viewers) | n/a |

### Payments backend inbound

| Port/Proto | Purpose |
|------------|---------|
| TCP 22 | SSH (optional) |
| TCP 8081 | Payments API (`http://<elastic-ip>:8081`) |

### Payments backend outbound

- `tcp/9090` to each orchestrator’s health endpoint (`http://<orchestrator-ip>:9090/health`).
- HTTPS to the configured Ethereum RPC (`ETH_RPC_URL`).

Ensure the orchestrator security group allows the payments Elastic IP on ports 8081 (API) and 9090 (health).

## 3. Environment Variables

### Orchestrator (`docker-compose.unreal.yml`)

Set these in `.env` on the orchestrator host before launching:

```
ORCHESTRATOR_ID=orch-001
ORCHESTRATOR_ADDRESS=0xYourPayoutWallet
PAYMENTS_API_URL=http://<payments-elastic-ip>:8081
ORCHESTRATOR_REGISTRATION_DELAY=10

# Optional metadata
ORCHESTRATOR_CAPABILITY=vtuber
ORCHESTRATOR_CONTACT_EMAIL=ops@example.com
ORCHESTRATOR_HOST_NAME=orch-001
ORCHESTRATOR_HOST_PUBLIC_IP=<override public IP>

# TURN credentials (generated by script)
TURN_STATIC_AUTH_SECRET=...
TURN_RELAY_INTERNAL_IP=172.31.x.x
TURN_REALM=your.domain
```

- `ORCHESTRATOR_HOST_PUBLIC_IP` is optional; if omitted, the registration helper auto-detects the public IPv4 via the EC2 metadata service.
- The helper waits `ORCHESTRATOR_REGISTRATION_DELAY` seconds (default 10) before contacting the payments API so the network path is ready.
- The helper synthesises `health_url` as `http://<public-ip>:9090/health` unless you set `ORCHESTRATOR_HEALTH_URL` explicitly.

Generate `.env.turn` with `./scripts/generate_turn_credentials.sh` whenever you redeploy.

### Payments backend (standalone repo)

```
PAYMENT_INTERVAL_SECONDS=60
PAYMENT_INCREMENT_ETH=0.00001606079
PAYMENT_PAYOUT_THRESHOLD_ETH=0.001
TOP_CONTRACT_ADDRESS=0x35Bcf3c30594191d53231E4FF333E8A770453e40
ETH_RPC_URL=https://arb1.arbitrum.io/rpc
ETH_CHAIN_ID=42161
PAYMENT_PRIVATE_KEY=<hex signer key>
PAYMENTS_DEFAULT_HEALTH_TIMEOUT=10
PAYMENTS_DEFAULT_MIN_SERVICE_UPTIME=80
PAYMENTS_AUDIT_LOG_PATH=/app/data/audit/registry.log
PAYMENTS_BOOTSTRAP_ORCHESTRATORS_PATH=/app/data/orchestrators.json
PAYMENTS_BOOTSTRAP_SKIP_RANK_VALIDATION=true
PAYMENTS_ADDRESS_DENYLIST=0xAddressOne,0xAddressTwo
PAYMENTS_MANAGER_IP_ALLOWLIST=203.0.113.10,127.0.0.1
```

`PAYMENTS_SINGLE_ORCHESTRATOR_MODE` now defaults to `false`; if you turn it back on, also populate `ORCHESTRATOR_ID`, `ORCHESTRATOR_ADDRESS`, and (optionally) `ORCHESTRATOR_HEALTH_URL` so the backend can auto-register that single node. The recommended approach remains letting each orchestrator POST to the API.

- `PAYMENTS_ADDRESS_DENYLIST` accepts a comma- or whitespace-separated list of 42-character payout wallet addresses. Any orchestrator that attempts to register using one of these addresses will receive a `403` and existing records will be held ineligible for payouts.
- `PAYMENTS_MANAGER_IP_ALLOWLIST` configures which source IPs are allowed to view orchestrator IP information (`host_public_ip`, `last_seen_ip`, `health_url`). Requests from any other address still receive the registry data, but the sensitive fields are redacted. Include the IP of the payments admin host (and any proxies that terminate TLS) here.

## 4. Registration Flow

1. **Stack start**: `./scripts/start_vtuber_unreal.sh start -d` brings up TURN, signaling, Unreal, script runner, and `orchestrator-registration` helper.
2. **Metadata collection**: the helper loads `.env`, `.env.turn`, and environment defaults, auto-detects the public IP, and builds JSON payload fields:
   ```json
   {
     "orchestrator_id": "orch-001",
     "address": "0x...",
     "capability": "vtuber",
     "contact_email": "ops@example.com",
     "host_public_ip": "18.x.x.x",
     "host_name": "orch-001",
     "health_url": "http://18.x.x.x:9090/health",
     "health_timeout": 10,
     "monitored_services": ["vtuber-unreal-game","vtuber-unreal-signaling","vtuber-turn-server"],
     "min_service_uptime": 80
   }
   ```
3. **POST to payments API**: `POST PAYMENTS_API_URL/api/orchestrators/register`.
4. **Payments backend**: stores metadata, emits audit events, polls the health endpoint each minute, credits balances when services are healthy, and triggers payouts once `PAYMENT_PAYOUT_THRESHOLD_ETH` is reached.

If an orchestrator’s public IP changes (e.g., instance restart without Elastic IP), rerun the helper or re-POST to the API. Using Elastic IPs for orchestrators eliminates the need to reconfigure security rules.

## 5. Deployment Checklist

### Payments EC2

1. Launch t3.small (or similar) in the correct VPC/subnet.
2. Allocate and associate an Elastic IP.
3. Open security group ports: `tcp/8081` (from orchestrator IPs, or `0.0.0.0/0` if you expect rotating hosts), `tcp/22` if SSH is needed.
4. Clone the payments backend repository, set its `.env`, run `docker compose up -d` from that project.

### Orchestrator EC2

1. Generate TURN credentials (`./scripts/generate_turn_credentials.sh`).
2. Ensure security group allows the ports listed in section 2 and outbound access to `http://<payments-ip>:8081`.
3. Launch the stack: `./scripts/start_vtuber_unreal.sh start -d`.

### Verify

- `curl http://<payments-ip>:8081/api/orchestrators` should list each orchestrator with a populated `health_url` and `last_seen` timestamp.
- `docker compose logs payments-backend -f` should show cycles such as `Eligible cycle → credited …` followed by `Submitted payment tx …` once the threshold is met.
- Pixel Streaming UI accessible at `http://<orchestrator-ip>:8080`.

## 6. Frequently Asked Questions

**Q: How do I reset the registry but keep existing balances?**  
A: Stop the payments backend (`cd payments-backend && docker compose stop payments-backend`), back up `payments-backend/data/balances.json`, and delete `payments-backend/data/registry.json` (plus the `.bak` variant). When you restart the stack the ledger file is reused so outstanding balances remain intact, while the registry repopulates from fresh registrations. Configure `PAYMENTS_ADDRESS_DENYLIST` before restarting so denylisted wallets remain blocked from re-registering.

**Q: How does the orchestrator know its public IP?**  
A: The registration helper queries the EC2 metadata service. Override with `ORCHESTRATOR_HOST_PUBLIC_IP` if you are behind a load balancer or NAT gateway.

**Q: Do I need to rerun the helper after an orchestrator reboot?**  
A: Yes; the helper runs at start-up and re-registers automatically. Ensure the service is enabled or run the script manually.

**Q: Can I run payments and Unreal on the same box?**  
A: Only for development. In production keep them separate to avoid GPU host restarts impacting payouts and vice versa.

**Q: Where do audit logs live?**  
A: `payments-backend/data/audit/payments-audit.log` inside the payments container (also shipped to Fluent Bit outputs). Each registration or cooldown transition appends a JSON line.

Following this guide keeps the payments pipeline resilient while minimizing manual updates when infrastructure changes.

## 7. Automated provisioning (legacy)

The old `scripts/provision_orchestrator.py` helper has been removed now that the
images and repo are public. To spin up new orchestrators, launch a GPU host
(e.g., g4dn.xlarge) with the required security group, install Docker + NVIDIA,
clone this repo, and follow the main README “New deployment” steps. Use your own
automation/Infra-as-Code if you want to replicate the previous workflow.
