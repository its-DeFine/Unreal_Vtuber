# Pixel Streaming Architecture & Operations

This document summarizes how the Unreal VTuber repository packages the Pixel Streaming stack, the lessons learned while containerizing it, and the main operational considerations when deploying on EC2 or on local hosts.

## High-Level Layout

```
+----------------------------------+        +----------------------------------+
| vtuber-unreal-game (container)   |        | vtuber-unreal-signaling (container)
|----------------------------------|        |----------------------------------|
| Image: ghcr.io/.../embody-ue-ps  |  --->  | Image: embody-signaling:latest
| Runs: Embody build + Pixel       |  WebRTC| Runs: Epic start.sh (Wilbur) with
| Streaming streamer, Xvfb         | stream | bundled node/npm dependencies
| ulimit: 1040 (nofile)            |        | Exposes 8080/8888/8889
+----------------------------------+        +----------------------------------+
                  |                                    |
                  |                                    v
                  |                        +-------------------------+
                  |                        | turn-server (coturn)    |
                  |                        | UDP/TCP 3478 + 49160-49200
                  |                        | Credentials from .env.turn
                  |                        +-------------------------+
                  v
        Client browsers via TURN/STUN
```

All services share the external Docker network `vtuber_network`, so the streamer connects to the signaling container using the internal DNS name `unreal-signaling`.

## Container Build Pipeline

1. **Game Image (`embody-pixel-streaming:latest`)**
   - Built by `docker/aws-pixel-streaming/package-embody.sh` when a new Embody build is produced.
   - Copies the build into `/opt/embody`, ensures scripts are executable, and leaves the bundled Pixel Streaming infrastructure in place.
   - The container entrypoint (`start-embody.sh`) launches Xvfb, applies the `nofile` limit, and runs `Embody.sh` with `PIXEL_STREAMING_URL` pointing at `ws://unreal-signaling:8888`.

2. **Signaling Image (`embody-signaling:latest`)**
   - Dockerfile: `docker/pixel-streaming/signaling/Dockerfile`.
   - Starts from the game image to reuse the packaged WebServers tree.
   - Installs `ca-certificates`, `curl`, and `xz-utils` (required by Epic scripts).
   - Writes `NODE_VERSION`, runs `setup.sh --nosudo --deps`, and executes `npm install` for Wilbur inside the image. No additional downloads are needed at runtime.
   - Entrypoint: `run-packaged-signaling.sh`, which exports the bundled Node on `PATH` and invokes Epic’s `start.sh` with compose-provided TURN/STUN env variables.

3. **TURN**
   - Uses the upstream `instrumentisto/coturn` image. Credentials and ports are sourced from `.env.turn` (generated by `./scripts/generate_turn_credentials.sh`).

## Lessons Learned

- **Bundled Node/npm must be present**: The Pixel Streaming scripts expect their own Node runtime under `platform_scripts/bash/node/bin`. Missing this caused `Cannot find module 'express'`. Packaging must include both `NODE_VERSION` and the Node tree.
- **`setup.sh` needs internet at build time**: Running it during the Docker build ensures Wilbur is ready. If run at runtime, the container would require outbound access, which complicates deployments.
- **CA certificates are required**: `setup.sh` and `start.sh` use `curl https://api.ipify.org` and other TLS endpoints. Installing `ca-certificates` inside the container prevents `curl: (77)` errors.
- **File descriptor limits**: The game crashes or loses websocket connections if `nofile` is too low. We set `HOST_ULIMIT_NOFILE=1040` and pass `ULIMIT_NOFILE=1040` into the game container so `/usr/local/bin/start-embody.sh` applies the correct limit.
- **TURN reachability is a client-side dependency**: The stack intentionally exposes UDP 3478 and the relay range 49160–49200. If a client network blocks outbound UDP, WebRTC will stall at “connection negotiated”. A quick sanity check is to run the Trickle ICE test page with the TURN credentials.
- **Compose vs. manual scripts**: Running Epic’s `start.sh` on the host helped identify missing dependencies, but ultimately the goal is a self-contained container. The current Dockerfile mirrors those host steps so compose deployments are turnkey.

## Operational Checklist

1. `git pull --rebase origin feature/vtuber-elevenlabs`
2. `./scripts/generate_turn_credentials.sh`
3. (Optional) `docker/aws-pixel-streaming/package-embody.sh /path/to/Embody/Linux`
4. `docker compose -f docker-compose.yml -f docker-compose.unreal.yml build unreal-signaling`
5. `docker compose -f docker-compose.yml -f docker-compose.unreal.yml up -d turn-server unreal-signaling unreal-game`
6. Verify logs and ulimit: `docker logs vtuber-unreal-signaling --tail 20`, `docker exec vtuber-unreal-game bash -lc 'ulimit -n'`
7. Connect via browser at `http://<public-ip>:8080`

Keep `.env.turn` secure—the credentials are shared between coturn and Wilbur. Regenerate the file whenever redeploying to rotate secrets.
